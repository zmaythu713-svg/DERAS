# DERAS Table Descriptions (Paragraph Form)

In DERAS, the database tables work together as one unified schema. The `academic_years` table stores school-year records used across the system. It contains fields such as `id`, `name`, `start_year`, `end_year`, `is_active`, `is_current`, and `status`. The field `id` serves as the primary key. The field `name` stores the academic year label (for example, 2025-2026). The fields `is_current` and `is_active` show which year is currently used for data entry. The `townships` table stores township information. It contains `id`, `name`, and `is_active`. The field `id` is the primary key, and `name` is the township name used in quota, allocation, and distribution modules. The `grades` table stores grade or class-level information with `id`, `name`, and `is_active`. Its primary key is `id`, and this table is referenced by textbooks, stocks, allocation plans, school supplies, and teacher guides. The `book_names` table stores subject or book titles with `id`, `name`, and `is_active`. Its primary key is `id`, and book names are linked to textbooks, stocks, allocation plans, and teacher guides through `book_name_id`. The `categories` table stores book-type categories used for grade–book mapping. It contains `id`, `slug`, `name_en`, `name_mm`, and `is_active`. The field `id` is the primary key, and the category name helps classify books in the mapping table. The `grade_book_names` table links grades, book names, and categories. It contains `id`, `grade_id`, `book_name_id`, and `category_id`. The field `id` is the primary key, while `grade_id`, `book_name_id`, and `category_id` are foreign keys that reference `grades`, `book_names`, and `categories`.

Student quota data is stored in a header–detail structure. The `quotas` table stores student quota headers by academic year and township. It contains `id`, `academic_year_id`, and `township_id`. The field `id` is the primary key, and `academic_year_id` and `township_id` are foreign keys. One quota record belongs to one year and one township. The `quota_lines` table stores detailed student quantities for each quota. It contains `id`, `quota_id`, `school_level`, `ownership`, and `quantity`. The field `id` is the primary key, and `quota_id` is a foreign key that references `quotas`. School level values include primary, middle, high, and agriculture, while ownership values include public, monk, and private. This header–detail design keeps the database normalized. The `school_counts` table stores the number of schools by academic year, grade, and township. It contains `id`, `academic_year_id`, `grade_id`, `township_id`, and `school_count`. The field `id` is the primary key, and the other id fields are foreign keys used in supply-related calculations.

Textbook planning and distribution also use linked tables. The `allocation_plans` table stores textbook allocation plan headers. It contains `id`, `academic_year_id`, `grade_id`, `book_name_id`, `sequence_no`, `received_books`, `books_per_package`, and related total fields. The field `id` is the primary key, and `academic_year_id`, `grade_id`, and `book_name_id` are foreign keys. This table supports planning before township distribution. The `allocation_plan_townships` table stores township-level details for each allocation plan. It contains `id`, `allocation_plan_id`, `township_id`, `previous`, `total_students`, and `transferable`. The field `id` is the primary key, and `allocation_plan_id` and `township_id` are foreign keys. This table replaces wide township-specific columns and keeps the design normalized. The `textbooks` table stores regular textbook distribution records. It contains `id`, `academic_year_id`, `township_id`, `grade_id`, `book_name_id`, `books_per_set`, `student_count`, `book_count`, and `remark`. The field `id` is the primary key, and the four related id fields are foreign keys. A unique combination of year, township, grade, and book name prevents duplicate rows. The `stocks` table stores extra or stock distribution records. It contains `id`, `academic_year_id`, `township_id`, `grade_id`, `book_name_id`, `previous_balance`, `transferred`, `enrolled_need`, `required_qty`, and `remark`. The field `id` is the primary key, and the related id fields are foreign keys used to track stock needs by location and book. The `previous_year_balances` table stores carry-forward balances for a new academic year. It contains `id`, `academic_year_id`, `township_id`, `grade_id`, `book_name_id`, and `balance`. The field `id` is the primary key, and the other id fields are foreign keys. This table supports rollover and balance lookup.

Teacher-guide processing follows a linked family of tables. The `teacher_guides` table stores teacher-guide receipt quotas. It contains `id`, `academic_year_id`, `grade_id`, `book_name_id`, `group_no`, `group_title`, `guide_type`, `sequence_no`, `kg_to_g12_quota`, `g1_to_g5_quota`, `total_quota`, and `remark`. The field `id` is the primary key, and `academic_year_id`, `grade_id`, and `book_name_id` are foreign keys. The `teacher_guide_township_allocations` table stores township distribution quantities for each teacher guide. It contains `id`, `teacher_guide_id`, `township_id`, `kg_g12_qty`, and `g1_g5_qty`. The field `id` is the primary key, and `teacher_guide_id` and `township_id` are foreign keys. The `teacher_guide_issues` table stores issue headers for teacher guides. It contains `id`, `teacher_guide_id`, `academic_year_id`, `grade_id`, `book_name_id`, `district_unit`, `package_unit`, and related fields. The field `id` is the primary key, and `teacher_guide_id` links the issue to the teacher-guide family. The `teacher_guide_issue_townships` table stores issued quantities by township. It contains `id`, `teacher_guide_issue_id`, `township_id`, and `issued_quantity`. The field `id` is the primary key, and `teacher_guide_issue_id` and `township_id` are foreign keys. The `teacher_guide_summaries` table stores summary balances and distributed totals. It contains `id`, `teacher_guide_id`, `previous_balance`, `fiscal_year_quota`, `total_books`, `distributed_books`, and `remaining_books`. The field `id` is the primary key, and `teacher_guide_id` is a foreign key that keeps summary data linked to the same guide family.

School supply data is stored in related item and allocation tables. The `school_supply_items` table stores supply item names and rates. It contains `id`, `name`, `rate`, and `is_active`. The field `id` is the primary key. The field `name` is the supply item name, and `rate` is used when calculating allocation quantity. The `school_supply_allocations` table stores allocated supply quantities. It contains `id`, `academic_year_id`, `grade_id`, `township_id`, `school_supply_item_id`, `school_count`, `quantity`, and related row fields. The field `id` is the primary key, and the related id fields are foreign keys. Quantity is commonly calculated as rate × school count. The `supply_items` table stores issue item names used in supply detail records. It contains `id`, `name`, and `is_active`, and `id` is the primary key. The `supply_details` table stores issued supply totals. It contains `id`, `academic_year_id`, `township_id`, `grade_id`, `supply_item_id`, `unit`, `issued_total`, `package_count`, and `loose_count`. The field `id` is the primary key, and the related id fields are foreign keys. The `company_contacts` table stores company or contact information used in related workflows. It contains `id`, `company_name`, `lot`, `responsible_name`, `phone`, and `is_active`, with `id` as the primary key.

User access is controlled through role-based tables. The `roles` table stores system roles such as Super Admin and Admin. It contains `id`, `name`, `slug`, and `description`. The field `id` is the primary key, and `slug` uniquely identifies the role in code. The `permissions` table stores named access rights. It contains `id`, `name`, `slug`, and `group`. The field `id` is the primary key. Permissions control actions such as viewing records, managing records, deleting records, managing users, and academic-year rollover. The `role_permission` table is the intersect table for roles and permissions. It contains `id`, `role_id`, and `permission_id`. The field `id` is the primary key, and `role_id` and `permission_id` are foreign keys. This table resolves the many-to-many relationship between roles and permissions. The `users` table stores login accounts for Admin and Super Admin. It contains `id`, `name`, `email`, `role`, `role_id`, `password`, `email_verified_at`, and `remember_token`. The field `id` is the primary key, and `role_id` is a foreign key that references `roles`. Email and password are used for login. After successful login, role-based permissions decide which modules the user can open.

Overall, these tables form a normalized relational design for DERAS. Master data tables provide shared references, operational tables store allocation and distribution records, and authentication tables control secure access for Admin and Super Admin users.
